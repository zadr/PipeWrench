## Your Job

Review every argument above. For each one, evaluate:
- Are the factual claims verified (file:line citations, actual code), or fabricated/assumed?
- Is the impact analysis complete? Did they consider: silent data loss, unbounded buffer growth, performance regression, thread safety implications?
- Is the "why others are wrong" section actually compelling or hand-waving?
- Did they identify the real RISK honestly, or bury it?

Then make your decision. Your options depend on the issue type:

### For retain cycles / leaks:

**A: Make a reference weak.** Only if: the target has a VERIFIED other strong owner, nil is impossible or handled correctly (not silently swallowed, not buffered forever), and it's a natural back-edge.

**B: Break at teardown.** Add `stop()`/`invalidate()`/`deinit` logic that nils out references. Choose this when no single `weak` is safe.

**C: Restructure with closure captures.** Use `[weak self]` in a closure instead of changing stored properties. Choose this when the cycle is through a closure.

### For heap growth:

**A: Add eviction/cap.** If objects accumulate without bound, add LRU eviction, a size cap, or TTL expiry.

**B: Reduce allocation size.** If individual allocations are too large, restructure (lazy loading, streaming, compression).

**C: Fix the lifecycle.** If objects outlive their usefulness, fix the ownership so they're released when no longer needed.

### For autorelease pool bloat:

**A: Add @autoreleasepool.** Wrap the tight loop or long-running operation.

**B: Avoid autoreleased temporaries.** Restructure to use stack-allocated or explicitly-managed values.

### For any issue type:

**E: Not worth fixing.** The issue is real but the cost of the change exceeds the cost of the problem. Choose this when:
- The impact is trivial (under 1 MB, handful of objects) AND there is no user-facing consequence (no OOM, no flaky tests, no performance degradation).
- The "issue" is normal framework behavior (e.g. XCTest retaining test case instances until suite end, system caches holding expected data).
- The fix has high blast radius (touches core types, changes DI contracts, modifies widely-used APIs) for a problem that causes no real harm.
- The memory is reclaimed naturally at an acceptable time (process exit, scene disconnect, next run loop turn).

Do NOT use E to avoid hard problems. If the issue causes real harm (user-facing memory pressure, OOM kills, flaky tests, unbounded growth), propose a fix even if it's risky. E is for genuinely low-value work.
